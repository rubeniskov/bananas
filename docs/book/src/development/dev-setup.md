# Dev environment

## Host requirements

You'll need a Linux host (x86_64) with:

- [`pixi`](https://pixi.sh/) — the project's environment manager (Python 3.11, `kas`, conda-side toolchain).
- A few system packages bitbake needs that conda doesn't ship cleanly: `chrpath cpio diffstat hostname/inetutils rpcsvc-proto`. Install via your distro's package manager.
- `docker` running natively (not Docker Desktop) — the network-boot dev loop uses TFTP and NFS containers that need to bind LAN ports the Desktop VM can't expose.
- `git` and `cargo` (the workspace cross-compile uses `cargo-zigbuild`; pixi will pull it in).

macOS works for editing docs and Rust crates, but the Yocto bake needs a Linux host.

## First-time host setup

Two one-time steps for the dev loop:

```bash
# Disable the native NFS server (the Docker NFS container will use the
# kernel's nfsd module — only one userspace can own it at a time).
sudo systemctl disable --now nfs-server

# Make sure the nfsd kernel module is loadable.
lsmod | grep -q '^nfsd' || sudo modprobe nfsd
```

No `/etc/exports` edits — the NFS container manages exports internally.

## The dev loop: `pixi run iterate`

Once the SD card is flashed, you almost never re-flash it. The dev loop boots the BPI over TFTP (kernel + DTB) and mounts its rootfs over NFS, so an `iterate` cycle is "rebuild → publish → reboot the board → done".

```bash
pixi run iterate    # the standard dev loop
```

What it does, in order:

1. Cross-compiles the bananas-* Rust crates to armv7 (`cargo-zigbuild`).
2. Bakes the Yocto image (`kas build kas.yml`).
3. Stages the kernel/DTB to `./serve/tftp/`.
4. Reboots the board (`ssh root@$BPI_HOST reboot`).
5. Waits for the board to stop responding to ping (`wait-board-down`).
6. Extracts the new rootfs into the NFS share via a throwaway alpine container.
7. Restarts the TFTP container so the next netboot picks up the new kernel.

The board comes back up running the freshly-baked image in ~30 seconds (depending on how much actually changed in the bake).

`BPI_HOST` is required for the reboot step:

```bash
BPI_HOST=bananapro.local pixi run iterate
```

## One-time U-Boot setup on the board

For TFTP+NFS netboot to work, paste this into the U-Boot serial console once and `saveenv`:

```
setenv serverip <host-server-ip>
setenv ipaddr <bpi-static-ip>
setenv netargs 'setenv bootargs console=ttyS0,115200 root=/dev/nfs nfsroot=<host-server-ip>:/nfsshare,vers=3 ip=dhcp panic=10'
setenv bootcmd_net 'run netargs; tftpboot 0x42000000 uImage; tftpboot 0x43000000 sun7i-a20-bananapro.dtb; bootm 0x42000000 - 0x43000000'
setenv bootcmd 'run bootcmd_net'
saveenv
```

The NFS path `/nfsshare` is the path *inside* the container — the Docker container bind-mounts `./serve/nfs/bananas` → `/nfsshare`.

## Building one recipe at a time

For tight iteration on a single Yocto recipe (e.g. when you're debugging a kernel patch or a new plugin's bake), don't re-run the whole `kas build`. Drop into a bitbake shell:

```bash
pixi shell
kas shell kas.yml -c 'bitbake bananas-cloud'                 # build just one recipe
kas shell kas.yml -c 'bitbake -c cleansstate bananas-cloud'  # nuke its sstate cache first
kas shell kas.yml -c 'bitbake -c devshell bananas-cloud'     # drop into the recipe's working dir
```

`kas` materialises upstream layers (`poky/`, `meta-openembedded/`, `meta-sunxi/`, `meta-arm/`) into the repo root and writes everything else under `build/` (configs, tmp, downloads, sstate-cache). Both the cloned layers and `build/` are gitignored — never commit them.

## Where things land in `build/`

| Path | What |
|---|---|
| `build/conf/local.conf` | Generated by kas from `kas.yml`'s `local_conf_header` block. Don't hand-edit. |
| `build/tmp/work/` | Per-recipe build dirs. `cd` into one for `devshell`. |
| `build/tmp/deploy/ipk/<arch>/` | Final `.ipk` files. The release pipeline picks specific ones from here for the gh-pages feed. |
| `build/tmp/deploy/images/<machine>/` | The bootable `.wic` image. |
| `build/sstate-cache/` | Shared state cache. Slow to fill on first build, fast on subsequent ones. |
| `build/downloads/` | Tarballs / git checkouts of upstream sources. Survives `cleansstate`. |

## Building the docs site locally

The mdbook source lives at `docs/book/`. To rebuild and preview:

```bash
mdbook build docs/book/
( cd docs/book/book && python3 -m http.server 8765 )
# Open http://localhost:8765/
```

The landing page (`docs/website/index.html`) is a single hand-written HTML file with embedded CSS — no build step. Edit it and refresh.

## Common gotchas

- **"Running in chroot, ignoring request"** when iterating — you're on an old `pixi.toml`. The fix shipped in the iterate-loop reorder; see [Troubleshooting](../troubleshooting.md).
- **`pixi run reboot` requires SSH key access** to the booted board. Drop your public key into `layers/meta-bananas/recipes-core/images/files/authorized_keys` before building. Root password stays unset; OpenSSH's `prohibit-password` blocks password auth.
- **A bbappend stops applying after a recipe version bump** — version-pinned appends like `elfutils_0.191.bbappend` are silent if the upstream recipe version changes. Watch for this when bumping the Yocto release line.
